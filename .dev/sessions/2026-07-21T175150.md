Fixed Maestro indexing documents into the wrong Elasticsearch index when multiple repos share one Kafka topic, since routing keyed on topic alone. Also bootstrapped this project's agentics devctx (previously only had `.dev/roadmap.md`).

- `kafka/repositoryUtils.ts`: `getRepoByTopic` replaced by `getMatchingRepos`: matches by categoryId/categoryAlias equality when a topic has more than one repo, fans out on a deliberate duplicate config, needs no identifier when a topic maps to only one repo. New `getConfiguredCategoryIds` returns the configured categoryId of every Lyric repo on a topic
- `kafka/processMessage/routeDocumentMessage.ts`: new; per-message routing extracted from `consumer.ts`'s `eachMessage`, testable without a live Kafka client. Parses once, routes, logs categoryId/categoryAlias/matched repos (plus `getConfiguredCategoryIds`'s output on a no-match) on every decision, DLQs unroutable messages with a warning. Each matched repo gets its own shallow payload copy, not a shared one, since a downstream handler mutates it directly
- `kafka/processMessage/documentMessage.ts`: `processDocumentMessage` takes an already-parsed payload, not the raw message
- `kafka/consumer.ts`: `eachMessage` delegates to `routeDocumentMessage`
- `packages/common/src/types/config.ts`: `LyricRepositoryConfig.categoryId` widened to `number | string`
- `apps/server/src/config/repositoryConfig.ts`: `LYRIC_CATEGORY_ID` no longer coerced to a number
- Tests: coverage for id/alias matching, fan-out, DLQ-on-no-match, per-repo failure isolation, `getConfiguredCategoryIds`, and the enriched no-match log
- `docs/usage.md`: documents categoryId/alias routing, fan-out, DLQ behaviour
- `.dev/roadmap.md`: deploy-ordering gap noted (Maestro's routing requires Lyric to also emit categoryId; agreed order is Maestro first)
- `AGENTS.md`/`CLAUDE.md`/`.dev/tech-debt.md`/`.dev/sessions/`: agentics devctx bootstrapped at 0.6.1
